# ec-driver

C++23 driver for Elite EC-series robot controllers (target robot: Annuo EA66,
a rebranded EC66; controller firmware V3.15.3). Builds on Linux and Windows,
and cross-compiles for 64-bit ARM Linux.

- `docs/ec66.md`: the robot and its controller, from the vendor's manuals, every statement sourced
  (reading notes in `docs/notes/`); §8 the open questions and the commands to settle them on the robot
- `docs/architecture.md`: the design: the robot as parts, the state mirror, workflows
- `docs/sdk_map.md`: the 184 SDK calls grouped by robot part (generated by `tools/sdk_map.py`)
- `docs/sdk_calls.md`: every SDK call from the manual, classified (remote-only, 8056 field)
- `docs/recording-format.md`: the raw and HDF5 recordings and the call log
- `docs/demo.md`: a checklist for showing the robot (5 to 10 minutes of checks, the demo, what to do when
  something goes wrong, notes for the audience)
- `docs/archive/`: superseded documents, kept for their history

## What is there

| Layer | What |
|---|---|
| transport | `ec::net::TcpSocket` (Linux + Windows, every blocking call with a timeout) |
| wire | `ec::sdk` (8055: the 184 typed calls, the JSON-RPC client), `ec::feedback` (8056: frames, reader, receiver thread), `ec::log` (8058: the controller's log) |
| robot | `ec::Robot` on two paths: the command connection (`robot.call(...)` and the parts `joint(i)`, `drives()`, `model()`, `safety()`, `io()`, `programs()`, `system()`, `motion()`) and the monitoring stream (`robot.monitor()`: the newest `ec::State`, by part, in SI); `ec::readiness` |
| motion | the motion controller's families in `ec::motion`: `Move` (joint, line, arc, rotate), `Path` (waypoints), `Jog`, `SpeedStream`, `ServoStream`, `Timestamped`; one open at a time; destroying an open one stops it |
| workflows | `ec::bring_up`, `ec::shut_down`, `ec::recover` with step-by-step reports; `ec::Session`: servos on for a scope, off at its end however it ends |
| recording | `ec::record`: raw recordings, HDF5 of `ec::State` (optional `ec::hdf5`), the call log |
| tools | `ec_monitor`, `ec_record`, `ec_query`, `ec_info`, `ec_log`, `ec_move`, `ec_play`; the sandbox `sbx_trajectory` |

Everything is tested without the robot: unit tests against scripted servers,
the tools end to end against a simulated arm (`tools/fake_robot.py`). On the
EA66 so far: the replies of the typed calls checked one by one, the rotation
convention measured, a timestamped circle run (`docs/ec66.md` §7).

In code:

```cpp
auto robot = ec::Robot::connect({.host = "192.168.0.200"}).value();
auto session = ec::Session::start(robot);          // brought up; servos off when it ends
if (!session) {
    std::print("{}", describe(session.error()));   // what bring-up did, and why it stopped
    return 1;
}

ec::motion::Move move(robot);
move.joint(q, {.speed = 0.1});                     // to joint positions [rad]
move.wait();
const ec::State s = robot.monitor().latest().value();   // 8056: as of its frame, free to read
auto T = robot.model().fk(s.positions()).value();       // 8055: asks the controller now
```

## The tools

All of them default to the robot at 192.168.0.200; `--help` on each. Those
that move the arm print their plan and move nothing without `--yes`; Ctrl+C
stops the arm.

    ./build/linux-release/apps/ec_info                      # versions, DH parameters, tools, frames, safety, start-up flags
    ./build/linux-release/apps/ec_log --level error --lines 20
    ./build/linux-release/apps/ec_monitor --rate 10          # the 8056 frames, as the pendant shows them
    ./build/linux-release/apps/ec_record --raw run.ecraw --h5 run.h5 --seconds 60
    ./build/linux-release/apps/ec_query getRobotMode         # one SDK call; --list, --check-all

    ./build/linux-release/apps/ec_move status                # the state, and what a motion still needs
    ./build/linux-release/apps/ec_move --yes bring-up        # or recover, shut-down
    ./build/linux-release/apps/ec_move --yes nudge 6 5       # J6 by +5 deg at 10 % speed

### A trajectory from a CSV file

`ec_play` runs a file of stamped TCP poses or joint positions (format in
`apps/ec_play.cpp`; examples in `examples/`):

    t,x,y,z,rx,ry,rz          # t [s], x y z [mm], rx ry rz [deg]: as the pendant shows poses
    0.0,-496,-122,424.431,180,0,90
    2.0,-436,-122,424.431,180,0,90

    t,j1,j2,j3,j4,j5,j6       # or joint positions [deg]

    ./build/linux-release/apps/ec_play path.csv                     # plans and checks it; nothing moves
    ./build/linux-release/apps/ec_play path.csv --yes               # bring-up, to the start, run, servos off
    ./build/linux-release/apps/ec_play path.csv --yes --speed 0.5 --record run.ecraw

Ready-made shapes are in `examples/` (star, square, circle, figure eight,
helix, and a cone: the tool tilting about a fixed tip, to check a TCP), all
about 60 mm, smoothly timed, written by `examples/shapes.py` around the fake
arm's pose. For your cell, set `CENTRE` and `TOOL` at the top of that file
from the pendant and run `python3 examples/shapes.py`; then `ec_play` each
file without `--yes` first.

Poses are solved by the controller's inverse kinematics near the joints now,
filled in every 3 mm and 1 deg, checked (no jump, no singularity, the limits),
and the joints follow a smooth spline through every point, at rest at both
ends, checked against their speed and acceleration limits
(`apps/planning.hpp`, the tools' planning: application code, not the
driver's). The run is the controller's timestamp service.

### Without the robot

Run the simulated arm in a second terminal and point the tools at it:

    python3 tools/fake_robot.py                  # 127.0.0.1: command 8055, monitor 8056, control 8057, log 8058
    ./build/linux-debug/apps/ec_play examples/joints_wave.csv --host 127.0.0.1 --yes

    python3 tools/fake_8056.py --chop --garbage  # the stream alone, with faults
    ./build/linux-debug/apps/ec_monitor 127.0.0.1

On Windows the binaries are `build\windows-release\apps\*.exe`.

## Build

Dependencies come from vcpkg in manifest mode (`vcpkg.json`, pinned baseline).
The HDF5 recording writer is optional: the presets enable it (vcpkg feature `hdf5`,
CMake option `EC_WITH_HDF5`); without it, everything else still builds.
Every preset builds into its own directory, `build/<preset>/`, including its
vcpkg packages, so Linux and Windows builds of the same checkout never collide.
`cmake --list-presets` shows only the presets for the current OS.

| Preset | Host | Builds |
|---|---|---|
| `linux-debug` | Linux | native, warnings as errors, AddressSanitizer + UBSan |
| `linux-tsan` | Linux | native, warnings as errors, ThreadSanitizer; without HDF5 |
| `linux-release` | Linux | native |
| `linux-aarch64` | Linux | cross, 64-bit ARM Linux |
| `windows-debug` | Windows | MSVC, warnings as errors |
| `windows-release` | Windows | MSVC |

The same three commands work for every preset:

    cmake --preset linux-debug
    cmake --build --preset linux-debug
    ctest --preset linux-debug

### Linux setup (once)

Needs GCC 13 or newer (for `<expected>` with C++23).

    sudo apt install -y build-essential cmake ninja-build curl zip unzip tar pkg-config git
    git clone https://github.com/microsoft/vcpkg ~/vcpkg
    ~/vcpkg/bootstrap-vcpkg.sh -disableMetrics
    echo 'export VCPKG_ROOT=$HOME/vcpkg' >> ~/.bashrc && source ~/.bashrc

`vcpkg.json` pins a vcpkg commit (`builtin-baseline`). If configuring fails
with "... exists on disk, but not in '<commit>'", the vcpkg clone is older than
that commit; update it with `git -C "$VCPKG_ROOT" pull`.

For `linux-aarch64` also:

    sudo apt install -y g++-aarch64-linux-gnu qemu-user   # qemu lets ctest run the ARM tests here

### Windows setup (once)

Install Visual Studio (2022 17.3 or newer, or 2026) with "Desktop development
with C++"; it includes CMake and Ninja. Then, in PowerShell:

    git clone https://github.com/microsoft/vcpkg $HOME\vcpkg
    & $HOME\vcpkg\bootstrap-vcpkg.bat -disableMetrics
    [Environment]::SetEnvironmentVariable("VCPKG_ROOT", "$HOME\vcpkg", "User")

Run the preset commands from the "Developer PowerShell" of your Visual Studio
version (it puts the MSVC compiler on the path), or open the folder in Visual
Studio / VS Code, which read `CMakePresets.json` directly.

### Formatting and static analysis

`.clang-format` defines the style; CI checks it with clang-format 22.1.8. Format
everything before committing (or let the editor format on save):

    pipx install clang-format==22.1.8      # once
    git ls-files '*.cpp' '*.hpp' | xargs clang-format -i

`.clang-tidy` enables bug-finding checks only; CI runs it with clang-tidy 22.1.8
and fails on any finding. It reads the compile commands of a configured build:

    pipx install clang-tidy==22.1.8        # once
    git ls-files '*.cpp' | xargs clang-tidy -p build/linux-debug --quiet

If it reports standard headers as not found (`'array' file not found`), clang
picked a GCC directory without C++ headers; name yours, e.g.
`--extra-arg=--gcc-install-dir=/usr/lib/gcc/x86_64-linux-gnu/15`.

### Continuous integration

`.github/workflows/ci.yml` checks formatting, then builds and tests all six
presets on every push to `master` and on every pull request, with the same
commands as above, and runs clang-tidy on the `linux-debug` build. The tests
include both tools, end to end against the fake servers (`tests/apps/`, Python
3 standard library; native builds only).

### Line endings

`.gitattributes` keeps every text file LF in the repository and in every
working tree, on both systems, regardless of each user's `core.autocrlf`.

## Layout

    include/ec/           public headers, one directory per namespace
      net/                TCP transport (all ports)
      sdk/                port 8055: one type per SDK call, codec, client
      feedback/           port 8056: frame, framer, reader, receiver thread
      log/                port 8058: the controller's log
      record/             recordings: raw, HDF5 (optional), the call log
      motion/             the motion controller (controller.hpp) and its families
      robot.hpp           ec::Robot
      monitor.hpp         ec::Monitor: the 8056 path, the newest ec::State (state.hpp)
      joint.hpp, drives.hpp, model.hpp, safety.hpp, io.hpp, programs.hpp, system.hpp
                          the parts: handles over the command connection
      readiness.hpp       what stands between the robot and a motion command
      workflows.hpp       bring_up, shut_down, recover, Session
    src/                  mirrors include/ec/; detail/ holds private headers
    apps/                 command-line tools on CLI11; the sandbox; the tools' planning (planning.hpp)
    examples/             trajectories for ec_play, written for the fake arm
    tests/                GoogleTest; support/ shared helpers; apps/ end-to-end tool tests
    tools/                fake controller ports (fake_8055.py, fake_8056.py, fake_robot.py), robot_checks.py
                          (read-only measurements), rotation_convention.py (how the convention was measured),
                          sdk_map.py (writes docs/sdk_map.md)
    docs/
    cmake/                warnings, cross toolchains

New API shapes (a facade, Python bindings, a ROS 2 wrapper) go in their own
top-level directory with their own CMake target, depending on `ec::driver`.
Other cross targets: add a toolchain file in `cmake/toolchains/` and a preset
that pairs it with the matching vcpkg triplet.
